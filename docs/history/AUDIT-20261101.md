## Findings fixed

1. The previous Windows staging folder was stale: its catalog source predated the interpreter guard and improved registration flow. The user therefore could still register `powershell.exe` as a script.
2. Replaced the minimal ListBox with a details ListView (name/status/mode), selected-script details, explicit log header, useful empty states and a responsive split layout.
3. Added file/folder browse controls to the edit dialog. Script name and default working directory follow the selected file until manually overridden.
4. Interpreter executables are rejected as script targets. Existing bad catalog records remain visible as `Исправить` and are blocked from launch instead of being silently dropped.
5. Catalog loading now falls back to the newest valid backup on malformed XML. Invalid or duplicate record IDs are repaired in memory; identical registrations are rejected.
6. Editing or deleting a live entry is blocked so the UI cannot lose control of a running process.
7. Stop now targets the verified owned PID tree with `taskkill /T /F`; the runner falls back to killing its direct child if tree termination fails.
8. Repo 2 worker continues to publish a temporary PID/start-time marker for compatibility with earlier test adapters. Repo 1 no longer checks this marker or Repo 2 process: the previous artificial ordering gate was removed from the working-copy adapter and MainForm, while the installed Windows quiet launcher/Guards remain unchanged.
9. Added one-click Fortis / RDG bundle import for five worker actions: Repo 2, Repo 1, RDG Updater, CI Watcher start and CI Watcher stop. The importer resolves worker paths relative to the running catalog folder, stores stable bundle IDs, prevents duplicates, and previews the external file dependencies already known from the worker sources.
10. Import is registration-only: it does not invoke workers, Docker, or existing services. Old mistaken `powershell.exe` catalog rows are left intact and explicitly warned about; the importer neither deletes nor rewrites them.
11. Added the user-requested **text-based import** dialog: multiline paste input, portable @app paths, absolute and environment-expanded paths, existing/deduplicated previews, no partial writes on invalid manifests and a manual final confirmation. Sample lines are stored in `TEXT-IMPORT-FORTIS-RDG.txt`.
12. On user request, removed **only** UI/adapter-level mandatory Repo 2 → Repo 1 ordering and the Repo 2 stop restriction from the working-copy ControlCenter and Repo1-Worker. The currently installed Windows Repo1 quiet launcher, Repo2 quiet launcher and their Guards were NOT touched. User's read-only Windows string checks found no explicit references to the other Repo in four installed launcher/Guard files, while Repo1 quiet/main and Repo2 Guard mentioned bootstrap/tmpfs. This is not a proof of cold-boot independence; shared Docker/DC/Git bootstrap remains a possible runtime constraint.

## Remaining limitations

- `Внутри центра` captures text stdout/stderr only; no stdin/TTY or embedding of arbitrary GUI windows.
- `Своё окно` opens a separate process window and does not capture its output.
- `taskkill /T /F` cannot guarantee termination of detached, re-parented or elevated descendants.
- The user's Windows catalog XML is outside this Docker workspace. The two existing `powershell` rows cannot be inspected or cleaned here; the new UI will flag interpreter paths as invalid so they can be corrected or removed manually.
- The actual installed Repo 2 and Repo 1 launchers were not executed. Worker marker/dependency logic requires Windows acceptance testing before using it for live connections.
- The text importer and five-entry Fortis / RDG bundle importer are statically tested only. Their Windows dialogs, catalog persistence and actual dependency statuses must be checked after compiling the updated `ScriptCatalog.cs` on Windows.
